# Pitfalls Research: RepoSage

## Critical Pitfalls

### P1. CSRF Token Store is In-Memory (Not Distributed-Safe)
- **File:** `backend/index.js` lines 175-210
- **Issue:** The CSRF token store (`csrfTokenStore` Map) is in-memory, explicitly documented as not working across multiple server instances. In production with multiple replicas, CSRF tokens generated by one instance are rejected by others.
- **Impact:** Multi-instance deployments will have intermittent CSRF failures under load. Users will see "CSRF validation failed" errors when requests hit different servers.
- **Prevention:** Replace the in-memory Map with a Redis-backed store (using the existing Redis client) before scaling beyond a single instance.
- **Priority:** HIGH (blocks horizontal scaling)

### P2. `repoReader.js` is Unwired — Prepared But Not Imported
- **File:** `backend/utils/repoReader.js` line 1
- **Issue:** This utility module has the comment "Prepared for future use — not yet wired into the backend pipeline." Tests exist but no consumer imports it.
- **Impact:** Any contributor refactoring the clone/read pipeline may not realize this module exists. Could lead to duplicated effort or inconsistent implementation.
- **Prevention:** During Phase 4 planning, decide whether to integrate `repoReader.js` or archive it. Document the decision in the module.
- **Priority:** MEDIUM (blocks clean refactoring of clone pipeline)

### P3. GitHub Action Duplicates Sensitive Logic from Backend
- **File:** `github-action/index.js` lines 25-47, `github-action/utils/`
- **Issue:** The GitHub Action maintains its own copies of:
  - Dangerous phrases list (hardcoded, not loaded from `shared-safety-config.json`)
  - Diff parsing (`utils/diffParser.js`)
  - Secrets scanning (`utils/secretsScanner.js`)
  - File extension allowlist
- **Impact:** Any security update to `shared-safety-config.json` or secrets scanning rules must be manually synced to the GitHub Action. The sync script (`scripts/sync-from-backend.js`) exists but is easy to forget.
- **Prevention:** Make the sync script part of the CI/CD pipeline. Better: Restructure the GitHub Action to fetch the shared config from a URL or use a shared npm package.
- **Priority:** HIGH (security rules will drift)

### P4. Analysis Cache is In-Memory (Not Distributed-Safe)
- **File:** `backend/utils/analysisCache.js` line 9
- **Issue:** `AnalysisCache` is an in-memory Map with a TODO comment about migrating to Redis. In multi-instance deployments, each server has its own cache — leading to redundant LLM calls and inconsistent behavior.
- **Impact:** Unnecessary Groq API costs in multi-instance deployments. Cache invalidation via webhook only affects the instance that received the webhook.
- **Prevention:** Implement Redis-backed cache using the existing `ioredis` client (already available in `index.js`).
- **Priority:** MEDIUM (affects cost at scale)

### P5. MongoDB Connection Required for Production — But Graceful Fallback is Fragile
- **File:** `backend/config/db.js` lines 27-33
- **Issue:** In production mode, the server crashes if MongoDB is unavailable. In non-production, it runs in degraded mode with file-based analytics. The transition between modes is not smooth and the degraded mode has limited testing.
- **Impact:** Production crashes if MongoDB goes down temporarily. No automatic reconnect — the process exits and must be restarted by the orchestrator.
- **Prevention:** Add automatic reconnection with exponential backoff in production mode instead of crashing.
- **Priority:** HIGH (production reliability)

## Moderate Pitfalls

### M1. Session TTL Design — 30 Min Creation, 24H Max Extension
- **File:** `backend/models/Session.js` + `backend/index.js` line 1120
- **Issue:** Sessions have a creation TTL of 30 minutes (preventing indefinite extension), but `lastAccessedAt` updates push `absoluteExpiry` up to 24 hours. If the calculation of `$max` is off, sessions could expire prematurely or never expire.
- **Impact:** Users could lose chat context after 30 minutes even while actively chatting, or stale sessions could accumulate.
- **Prevention:** Review the TTL index configuration and `$max` update logic carefully.

### M2. Model Allowlist Hardcoded in Backend
- **File:** `backend/index.js` line 53
- **Issue:** The `ALLOWED_ANALYSIS_MODELS` array is hardcoded with 4 model names. Adding a new model requires a code change. The AI Engine has its own mapping logic in `get_groq_model()`.
- **Impact:** Adding models (e.g., when Groq releases new ones) requires coordinated changes in two places.
- **Prevention:** Move model config to environment variables or the shared config file.

### M3. Temp Repo Cleanup Not Guaranteed on Crash
- **File:** `backend/index.js` line 2203 (TODO comment)
- **Issue:** Issue #397 documents that temp repo folders leak if the Node process crashes during analysis. The current cleanup only runs on `SIGINT`/`SIGTERM`.
- **Impact:** Disk space leaks over time if the process crashes repeatedly.
- **Prevention:** Implement startup cleanup of stale `temp_repos` directories, or use OS-level temp directories.

### M4. CSRF Token Store Can Grow to 10,000 Entries
- **File:** `backend/index.js` lines 196-208
- **Issue:** The in-memory CSRF token store caps at 10,000 entries with oldest-entry eviction. If token generation exceeds cleanup, memory grows to the cap.
- **Impact:** Memory usage scales with active users. 10,000 tokens × ~32 bytes = ~320KB minimum, but with Map overhead it's more.
- **Prevention:** Reduce cap, increase cleanup frequency, or switch to Redis.

### M5. No Frontend Test Coverage
- **Files:** `frontend/src/` (only `useDebounce.test.tsx`, `useStore.test.js`, `sanitize.test.js`, `exportUtils.test.js`)
- **Issue:** Only 4 test files exist for the frontend. Dashboard.tsx has no tests. Components have no tests.
- **Impact:** Frontend changes risk regression. GSSoC contributors have no test examples to follow.
- **Prevention:** Add component tests as part of Phase 4 work.

### M6. `API.md` is Incomplete
- **File:** `API.md`
- **Issue:** The API docs don't cover most backend endpoints (`/api/chat`, `/api/webhook`, `/api/reports/pdf`, analytics endpoints, session endpoints, etc.) and the structure doesn't match the actual response schemas.
- **Impact:** Contributors and API consumers have incomplete documentation.
- **Prevention:** Auto-generate API docs from OpenAPI/Swagger specs, or complete the manual documentation.

## Minor Pitfalls

### m1. Backend Tests Run Sequentially (No Parallel Execution)
- **File:** `backend/tests/run-tests.js`
- **Issue:** Test files are run one at a time. With 67 test files (many with tests that mock different env vars), the suite takes a while.
- **Impact:** Slow CI feedback loop.
- **Prevention:** Enable parallel test execution where possible.

### m2. No Prettier/ESLint Configuration in AI Engine
- **File:** `ai-engine/` (no `.eslintrc` or `.prettierrc`)
- **Issue:** Root-level ESLint and Prettier configs only cover JS/TS. Python code in the AI engine has no linting configured.
- **Impact:** Python code quality inconsistencies.
- **Prevention:** Add `flake8`/`black` configuration to `ai-engine/`.

### m3. Hardcoded Port Numbers in Multiple Places
- **Issue:** Port 5000, 8000, 3000 appear in `.env.example` files, `docker-compose.yml`, README, and code.
- **Impact:** Changing ports requires updating many files.
- **Prevention:** Centralize port configuration.

### m4. `contribs.json` and Other Data Files in Root
- **File:** Root directory contains `contribs.json`, `vars.json`, `prs.txt`, `test.py`, etc.
- **Issue:** Root directory clutter from CI/automation scripts mixed with source code.
- **Impact:** Confusing for new contributors navigating the repo.
- **Prevention:** Move data/script artifacts to a `scripts/` or `ci/` subdirectory.

## Phase-Specific Warnings

### Phase 4 (Community & Scale) — Watch Out For
1. **Dashboard Audit History** needs careful MongoDB query optimization (pagination + filtering)
2. **.reposageignore support** must integrate with `ignoreHelper.js` and the clone pipeline
3. **PDF Export** (already partially implemented) — needs styling polish
4. **Plugin Architecture** is the most architecturally complex — needs design discussion first

### Phase 5 (GSSoC Epics) — Watch Out For
1. **VS Code Extension** is in early stages — needs activation event handling and error recovery hardening
2. **RAG System** is functional but the fallback embedding mode produces zero vectors — results will be poor without sentence-transformers
3. **Multi-Repo Analytics Dashboard** — needs aggregate queries and possibly pre-computed rollups
4. **Sync drift**: All three epics will need to stay in sync with the shared backend API

## Security-Specific Concerns

1. **API Key in URL**: `REPOSAGE_API_KEY` is passed as a query-like header, not a proper auth scheme — could leak in logs
2. **Webhook Secret Validation**: Uses `verifyWebhookSignature` with HMAC — correct, but `WEBHOOK_SECRET` must be strong
3. **Session Token Storage**: `sessionOwnerToken` is returned to the frontend — must be treated as sensitive by consumers
4. **GitHub PAT**: Stored in env vars, used for repo cloning and PR creation — needs careful permission scoping
5. **CORS Configuration**: AI Engine CORS is restricted but defaults to `http://localhost:5000` only
